## Что меняем

Сейчас приложение собирается для Android TV и телефонов; платформенного проекта iOS нет. Цель — согласовать идентичность dev/prod, добавить сборку и базовый запуск iPhone Simulator, сохранить полный обязательный Android gate и предоставить отдельный опциональный iOS E2E через Melos. Запуск и сборка обеих платформ получают единый выбор JSON-окружения и согласованные профили VS Code.

Наблюдаемый результат: dev/prod имеют отдельные идентификаторы, настройки и сессии; Android launcher различает их названиями «AniStar TV Dev» и «AniStar TV». Melos и VS Code используют один файл окружения для каждого flavor; оба iOS flavor собираются и запускают существующий мобильный интерфейс. Android TV/mobile полностью проходят fixture E2E и проверку production-подписи. Полный iOS-путь входа, восстановления, каталога, HLS и возврата доступен для отдельного запуска; его пропуск явно означает «не проверено» и не блокирует обязательные проверки. Дополнительная цель iPad Simulator позволяет по выбору осмотреть широкую мобильную компоновку и принудительный TV-профиль. Завершённое изменение получает общую новую версию приложения, запись CHANGELOG и проверенный PR в `main`.

### Входит

- CAP-01 — новые Android application ID и отдельная установка без переноса локальных данных.
- CAP-02 — iOS runner, созданный штатным генератором закреплённого Flutter, с последующей настройкой dev/prod и воспроизводимым запуском на iPhone Simulator.
- CAP-03 — вход и восстановление сессии на iOS с изоляцией защищённого хранилища и preferences.
- CAP-04 — прямое нативное HLS на iOS с сохранением контракта источника, управления и восстановления.
- CAP-05 — управление удержанием экрана и жизненным циклом плеера на iOS.
- CAP-06 — основной мобильный сценарий iPhone: клавиатура, SafeArea, ориентация, сенсорное управление и возврат; дополнительная опциональная диагностика широкого экрана на iPad Simulator.
- CAP-07 — обязательный Android fixture E2E TV/mobile, отдельная опциональная Melos-команда iOS E2E и актуальные документы запуска, контрактов и границ подтверждения.
- CAP-08 — повышение общей версии Android/iOS и CHANGELOG по фактически завершённому изменению.
- CAP-09 — после реализации, обязательных проверок и технического ревью: commit, push рабочей ветки и PR в `main`.
- CAP-10 — единая несекретная конфигурация через `--dart-define-from-file`, публичная Melos-команда `env:prepare` и сохранение существующего локального prod-файла.
- CAP-11 — переносимые настройки VS Code: закреплённый SDK, dev/prod F5 debug, существующий dev profile для поддерживаемой Android-цели и явные Melos tasks.

### Не входит

Полноценная продуктовая поддержка iPad, tvOS, физические устройства Apple как цели приёмки, Apple device signing, App Store/TestFlight и распространение сборок. Диагностика на iPad не добавляет автоматический TV-профиль по ширине или пользовательский переключатель профиля. Не входят перенос данных старого Android-приложения, новый дизайн интерфейса, замена playback-стека, браузер или медиапрокси, скачивание и офлайн-просмотр. Merge PR, tag, GitHub Release и публикация приложения не входят в поручение.

## Как будет работать

### Подготовка платформы и завершение изменения

В корне существующего AniStar TV исполнитель сначала запускает `fvm flutter create --platforms=ios --no-pub .` закреплённым SDK, без `--overwrite`. Затем проверяет diff и сохранность существующих Android/Dart-файлов, тестов, pub workspace и пользовательских правок, выполняет штатную подготовку зависимостей по lockfile. Только после генерации настраивает bundle ID, dev/prod, регистрацию plugins и платформенные контракты AniStar.

Общая подготовка окружения по D-13 применяется к CLI и IDE. Для F5 выбираются профиль и устройство в VS Code; `preLaunchTask` готовит только env-файлы по D-14.

После завершения функциональности исполнитель повышает общую версию и оформляет CHANGELOG по D-10, включая настройку Android, единое окружение и VS Code. Обязательные проверки и техническое ревью относятся к итоговому изменению с новой версией. При успешном завершении он делает commit, push рабочей ветки и создаёт PR в `main` по D-11; отчёт различает обязательные результаты и опциональные проверки.

### Основной поток

Ниже задано поведение приложения. Полное прохождение этого потока на iOS относится к отдельно запускаемому E2E по D-07; обязательная проверка iOS ограничена сборкой и базовым запуском по D-03.

1. Разработчик выбирает dev или prod в Melos либо VS Code. Общая подготовка проверяет JSON; отсутствующий локальный prod-файл создаётся из публичного шаблона по D-13. Сборка получает соответствующие идентификатор, точку входа и обязательный `--dart-define-from-file`; оба flavor могут быть установлены одновременно.
2. Новый Android-экземпляр устанавливается рядом с прежним. Он начинает с собственных настроек и формы входа по D-02.
3. На iPhone Simulator приложение выбирает мобильный профиль. Старт проверяет зеркало, затем читает и проверяет сессию выбранного flavor.
4. При отсутствии сессии пользователь вводит логин и пароль. Только подтверждение сайта и успешное сохранение сессии открывают каталог. Повторный запуск проверяет сохранённую сессию без повторного POST пароля.
5. Пользователь открывает сериал и серию. Репозиторий получает свежий источник; native player открывает HLS с полным URI и заданными заголовками. Доступны пауза, перемотка, смена качества и серии.
6. Во время активного воспроизведения экран удерживается включённым. Уход в фон приостанавливает видео и снимает удержание; возврат возобновляет только ранее игравшее видео.
7. Возврат из плеера освобождает его ресурсы и восстанавливает мобильную ориентацию и системный интерфейс. Выход из аккаунта удаляет сессию текущего origin; следующий запуск показывает вход.

### Исключения и развилки

| Условие | Поведение | Связанное решение |
| :--- | :--- | :--- |
| Локального `env/prod.json` нет | `env:prepare` проверяет публичный шаблон и создаёт локальный файл; последующие запуски читают его | D-13 |
| `env/prod.json` уже существует | Подготовка проверяет его и сохраняет содержимое; обновление шаблона не перезаписывает локальную настройку | D-13 |
| JSON повреждён, обязательный dev-файл отсутствует либо отсутствует нужный шаблон | Понятный отказ до Flutter-сборки/запуска; содержимое файла и credentials не печатаются. F5 также останавливается на подготовке | D-13, D-14 |
| В VS Code выбран iPhone Simulator | Используется dev/prod debug; Android dev profile не считается поддерживаемым режимом iOS Simulator | D-03, D-14 |
| Требуется production release APK | Запускается отдельная Melos task с production key/pin и проверкой артефакта; обычный F5 не запускает release | D-14 |
| Неверный пароль или неподтверждённый ответ сайта | Каталог закрыт; безопасная ошибка и возможность повторного входа. HTTP 200 сам по себе не означает успех | — |
| Ошибка сети при восстановлении или отказ Keychain | Старт остаётся в состоянии ошибки с ручным повтором. Сетевая ошибка не удаляет сохранённую запись; отказ хранилища не становится отсутствующей сессией | D-04 |
| Гостевая форма вместо защищённой страницы, выход или смена origin | Прежняя защищённая навигация и плеер закрываются; поздние ответы не восстанавливают старый аккаунт | — |
| Запрошенное качество недоступно | Выбирается наибольшее доступное из поддерживаемых; применённое качество отражается только после успешной инициализации | — |
| Ошибка HLS, инициализации или команды плеера | Один автоматический refresh с сохранением позиции и паузы; следующая ошибка оставляет ручной повтор. Новая серия начинается с нуля | D-05 |
| Пауза, буферизация, завершение, ошибка, другая страница или фон | Удержание экрана снято; поздний результат инициализации не запускает видео в фоне | D-06 |
| iOS E2E не выбран или его среда недоступна | Отметить iOS E2E и native HLS как непроверенные; обязательный Android gate и отдельную iOS сборку/базовый запуск оценить по их собственным результатам | D-07 |
| Явно запущенная iOS-проверка выявила несовместимость HLS | Сохранить конкретный сбой и вернуть в planning, если требуется изменение решения; опциональность не превращает найденную ошибку в успех | D-05, D-07 |
| Выбрана диагностика на iPad Simulator | Mobile остаётся исходным профилем; TV задаётся явно только в диагностическом запуске. Ширина и поворот сами профиль не меняют | D-08 |
| Генерация затронула существующие файлы вне нужной платформенной настройки | Проверить каждое изменение относительно исходного состояния; сохранить пользовательские правки и действующее приложение, не принимать шаблонную замену автоматически | D-09 |
| К завершению изменилась исходная версия приложения | Пересчитать следующий MINOR и строго больший build по актуальной базе, сохранить новые записи CHANGELOG | D-10 |
| Обязательная проверка или ревью не завершены либо GitHub недоступен | Не объявлять итог готовым и PR созданным; сохранить выполненное и точное условие продолжения. Пропуск опционального iOS E2E сам по себе не препятствует PR | D-07, D-11 |

### Самодостаточный пример iOS-конфигурации

Пример ниже задаёт связи конфигурации для AniStar TV после штатной генерации платформы. Для его применения достаточно этого плана, исходников AniStar TV и закреплённого Flutter SDK. Таблицы описывают целевую настройку, а не уже существующий `ios/`.

**Схемы и конфигурации.** Один target `Runner`, две общие схемы Xcode с именами строго `dev` и `prod`; обе схемы доступны Flutter CLI. Имя flavor после дефиса в конфигурациях записывается строчными буквами.

| Конфигурация | Схема | `PRODUCT_BUNDLE_IDENTIFIER` | Базовая Flutter-конфигурация | Тип CocoaPods, если используется |
| :--- | :--- | :--- | :--- | :--- |
| `Debug-dev` | `dev` | `com.anistar.tv.dev` | `Debug.xcconfig` | `:debug` |
| `Profile-dev` | `dev` | `com.anistar.tv.dev` | `Release.xcconfig` | `:release` |
| `Release-dev` | `dev` | `com.anistar.tv.dev` | `Release.xcconfig` | `:release` |
| `Debug-prod` | `prod` | `com.anistar.tv` | `Debug.xcconfig` | `:debug` |
| `Profile-prod` | `prod` | `com.anistar.tv` | `Release.xcconfig` | `:release` |
| `Release-prod` | `prod` | `com.anistar.tv` | `Release.xcconfig` | `:release` |

| Действие схемы Xcode | Схема `dev` | Схема `prod` |
| :--- | :--- | :--- |
| Run, Test, Analyze | `Debug-dev` | `Debug-prod` |
| Profile | `Profile-dev` | `Profile-prod` |
| Archive | `Release-dev` | `Release-prod` |

Profile/Release и Archive здесь обеспечивают согласованность проекта. Первая обязательная проверка на симуляторе использует Debug для обоих flavor; таблица не добавляет архивирование, подпись устройства или распространение iOS в объём работ.

**Настройки Flutter и плагинов.** Базой Xcode остаются Flutter `Debug.xcconfig`/`Release.xcconfig` либо их обёртки для flavor. Они включают `Generated.xcconfig`, который создаёт Flutter. При использовании CocoaPods соответствующие конфигурации также подключают сгенерированные настройки Pods своего режима; Xcode не должен обходить Flutter-конфигурацию и ссылаться только на `Pods-Runner*.xcconfig`. В `Podfile` все шесть имён из таблицы получают указанный тип. Если текущий SDK и выбранные плагины используют Swift Package Manager, сохраняется созданная SDK интеграция; добавлять CocoaPods только ради примера не требуется. Ни `Generated.xcconfig`, ни файлы Pods, ни другие временные результаты сборки вручную не редактируются. Регистрация плагинов и жизненный цикл runner следуют шаблону текущего SDK.

**Точки входа и окружения.** Общая таблица Android/iOS в разделе окружения ниже задаёт `lib/main_dev.dart` / `lib/main_prod.dart` и соответствующие обязательные env-файлы. Для CLI передаются `--flavor dev --target lib/main_dev.dart --dart-define-from-file=env/dev.json` или `--flavor prod --target lib/main_prod.dart --dart-define-from-file=env/prod.json`, плюс выбранный режим. Вызов следует успешному `env:prepare`; iOS E2E применяет тот же выбор app-конфигурации при своём явном запуске. Fixture harness сохраняет изолированное тестовое окружение и не переписывает локальную конфигурацию для доступа к fixture.

Поле аргументов LaunchAction в Xcode само по себе не заменяет настройку точки входа и Dart defines на этапе Flutter-сборки. Параметры одной схемы не должны случайно наследоваться от последней сборки другой. В VS Code точка входа задаётся через `program`, без дополнительного `--target`.

**Идентичность и версия.** Настройки в таблице задаются для всех трёх конфигураций каждого flavor. `Info.plist` использует следующие связи:

| Ключ `Info.plist` | Значение | Источник |
| :--- | :--- | :--- |
| `CFBundleIdentifier` | `$(PRODUCT_BUNDLE_IDENTIFIER)` | Bundle ID соответствующей конфигурации из первой таблицы |
| `CFBundleShortVersionString` | `$(FLUTTER_BUILD_NAME)` | `X.Y.Z` из корневого `pubspec.yaml` |
| `CFBundleVersion` | `$(FLUTTER_BUILD_NUMBER)` | `N` из корневого `pubspec.yaml` |

После согласованного повышения при текущей базе базовая версия — `1.3.0` и build `6` на обеих платформах; Android dev сохраняет суффикс `-dev` у `versionName`. Отдельный жёстко заданный номер версии в iOS или зависимость версии от выбранной схемы не вводятся. Dev/prod сохраняют отдельные preferences и области Keychain по D-04. Возможности и entitlements добавляются только для нужных AniStar функций; общий доступ между flavor, push, app groups или послабления ATS не следуют из этого примера. Portrait и landscape сохраняются по мобильному контракту; диагностический TV-профиль на iPad остаётся опциональным по D-08.

**Проверка связей.** Сопоставить список схем и конфигураций с таблицами, затем при обязательной сборке/базовом запуске dev и prod проверить фактические Bundle ID и X.Y.Z/N в артефактах, правильную точку входа и окружение. Успешная сборка одного flavor не подтверждает второй. Проверка этих связей не превращает полный iOS E2E в обязательный; Keychain restore, HLS и диагностика iPad сохраняют политику D-07/D-08.

### Самодостаточный пример Android-конфигурации

Android сохраняет dimension `environment` и flavors `dev`/`prod`. Идентичность установки задаёт Gradle; Dart JSON содержит только настройки приложения.

| Настройка | `dev` | `prod` |
| :--- | :--- | :--- |
| Базовый `applicationId` | `com.anistar.tv` | `com.anistar.tv` |
| `applicationIdSuffix` | `.dev` | Нет |
| Итоговый ID | `com.anistar.tv.dev` | `com.anistar.tv` |
| Launcher label через ресурс flavor | `AniStar TV Dev` | `AniStar TV` |
| `versionCode` | Flutter build number | Flutter build number |
| `versionName` | Flutter version name + существующий `-dev` | Flutter version name |
| При текущей целевой версии | `1.3.0-dev`, build `6` | `1.3.0`, build `6` |
| Точка входа и JSON | `lib/main_dev.dart`, `env/dev.json` | `lib/main_prod.dart`, `env/prod.json` |

Manifest получает label из соответствующего ресурса flavor, чтобы различение работало в телефонном и TV launcher. Сохраняются текущие namespace `com.anistar.anistar_tv`, package нативного кода и имена MethodChannel. Сохраняются `LAUNCHER`, `LEANBACK_LAUNCHER`, TV banner, icon/splash, необязательные touchscreen/leanback и действующая граница доверия HTTPS fixtures только в debug. Различение dev не требует смены графических ресурсов или TV-навигации.

Существующие JDK 17, Flutter/Gradle/AGP/NDK, SDK levels и параметры оптимизации остаются согласованы с закреплённым стеком. Production key, `.private/`, pin, signing guard и проверка AOT/JNI сохраняются. Debug/profile не загружают production credentials; production release APK проходит отдельный Melos wrapper с проверкой подписи и metadata. Декодирование Dart defines в Gradle и новый JSON-ключ `FLAVOR` не нужны: native flavor, ID и label уже задаются нативной конфигурацией.

### Общее окружение Android/iOS, CLI и IDE

Публичная команда `fvm dart run melos run env:prepare` становится единственным контрактом подготовки файлов. Она проверяет обязательный `env/dev.json`; существующий `env/prod.json` проверяет без перезаписи. Если prod отсутствует, проверяет `env/prod.example.json` и создаёт из него локальный prod. После подготовки оба файла доступны для сборки. Повторный вызов идемпотентен; ошибка чтения, JSON или создания прекращает подготовку и не запускает Flutter. Диагностика указывает файл и безопасную причину, без вывода содержимого.

| Flavor | Канонический файл для `--dart-define-from-file` | Подготовка | Хранение |
| :--- | :--- | :--- | :--- |
| `dev` | `env/dev.json` | Проверить наличие и валидность | Публичная несекретная конфигурация в Git |
| `prod` | `env/prod.json` | Проверить существующий; создать из валидного `env/prod.example.json` только при отсутствии | Локальный ignored-файл, не добавляется в Git |

JSON содержит несекретные параметры приложения, задаваемые при сборке; сейчас это строковый `ANISTAR_MIRROR_URL` с допустимым HTTPS origin по действующему контракту. Пароли, cookies, секреты подписи и данные live-аккаунта не помещаются в эти файлы и не передаются обычному запуску. Публичный шаблон сохраняет текущую настройку зеркала; произвольные новые ключи не вводятся.

Melos run/build wrappers обеих платформ вызывают общий подготовитель и всегда передают канонический файл выбранного flavor. VS Code вызывает его через `preLaunchTask`. Прямой запуск из корня выполняется последовательно: сначала `fvm dart run melos run env:prepare`, затем, например, `fvm flutter run --debug --flavor dev --target lib/main_dev.dart --dart-define-from-file=env/dev.json` либо `fvm flutter run --debug --flavor prod --target lib/main_prod.dart --dart-define-from-file=env/prod.json`. Для прямого Android debug/profile процесса также задаётся `ANISTAR_ANDROID_SIGNING_MODE=unsigned`. Сама команда `flutter` не вызывает подготовитель. Отдельно выбранный iOS E2E использует общий выбор app-конфигурации, сохраняя fixture harness и тестовую точку входа. Публичный `prod.example.json` служит только шаблоном создания: он не является отдельным окружением запуска IDE. Старый неявный запуск prod без файла заменяется D-13.

### Самодостаточный пример VS Code

Существующая `.vscode/` обновляется точечно. Настройка workspace `dart.flutterSdkPath` — `.fvm/flutter_sdk`; он выбирает SDK из `.fvmrc`, как Melos. Абсолютные пути машины, закреплённый `deviceId` и глобальные пользовательские настройки не требуются.

| Профиль | `program` | `flutterMode` | Элементы `toolArgs` | Цель |
| :--- | :--- | :--- | :--- | :--- |
| `Development` | `lib/main_dev.dart` | `debug` | `--flavor`, `dev`, `--dart-define-from-file=${workspaceFolder}/env/dev.json` | Выбранное Android-устройство или iPhone Simulator |
| `Production` | `lib/main_prod.dart` | `debug` | `--flavor`, `prod`, `--dart-define-from-file=${workspaceFolder}/env/prod.json` | Выбранное Android-устройство или iPhone Simulator |
| `Profile` | `lib/main_dev.dart` | `profile` | `--flavor`, `dev`, `--dart-define-from-file=${workspaceFolder}/env/dev.json` | Только Android-цель, поддерживающая profile |

Общие поля всех трёх профилей: `type: dart`, `request: launch`, `cwd: ${workspaceFolder}`, `preLaunchTask: env:prepare`. `env` процесса явно задаёт `ANISTAR_ANDROID_SIGNING_MODE: unsigned`, чтобы унаследованная настройка shell не загрузила production credentials во время F5. Это настройка процесса Gradle, не Dart define; debug APK сохраняет обычную SDK debug-подпись. `program` уже задаёт точку входа, поэтому `--target` не дублируется. Flutter CLI flags находятся в `toolArgs`; `args` не используется для `--flavor`, defines или режима. Устройство выбирается средствами VS Code.

| Задача workspace | Действие | Когда запускается |
| :--- | :--- | :--- |
| `env:prepare` | Из корня вызывает `fvm dart run melos run env:prepare` | Перед F5 и отдельно по выбору; без дополнительных зависимостей |
| Существующие задачи Melos | Сохраняют генерацию, check, clean/get, build, format/analyze, unit и Android E2E | Явно выбранная команда; TV и mobile E2E обязательны в полном Android gate |
| Production release APK | Вызывает `fvm dart run melos run build:android:prod:apk` с текущим signing/verifier контрактом | Явно выбранная сборка; не launch-профиль F5 |
| iOS E2E | Вызывает планируемую `fvm dart run melos run test:e2e:ios` с документированным выбором flavor/симулятора | Только отдельный явный выбор |
| Существующие live-задачи | Сохраняют явный Melos live-запуск | Только при отдельном разрешении; не зависимость запуска или подготовки |

F5 не запускает генерацию, полный gate, Android/iOS E2E или live. Рекомендации расширений включают `Dart-Code.dart-code` и `Dart-Code.flutter`; DCM и другие применимые существующие рекомендации сохраняются. Автоматическая установка расширений и изменение глобальных пользовательских настроек в область не входят.

## Ключевые решения

| ID | Решение | Почему | Применимость | Проверка/ограничение |
| :--- | :--- | :--- | :--- | :--- |
| D-01 | На Android и iOS prod — `com.anistar.tv`, dev — `com.anistar.tv.dev` | `user_acceptance_observation`: пользователь подтвердил общий набор ID | CAP-01, CAP-02 | Проверять metadata артефактов и раздельную установку. Android namespace и имена MethodChannel не переименовывать автоматически |
| D-02 | Android переходит отдельной чистой установкой без переноса локальных данных; старое приложение и его данные сохраняются. Production key, публичный pin и `.private/` сохраняются | `user_acceptance_observation`: выбран переход без миграции; исходный intent требует сохранить подпись и старую установку | CAP-01, CAP-03 | Новый экземпляр требует входа; серверные данные читаются обычным протоколом. Автоматического удаления старого приложения и экспорта cookies нет |
| D-03 | Первая обязательная цель — сборка и базовый запуск dev/prod на iPhone Simulator с существующим mobile UI; оба flavor проверяются в режиме debug | `user_acceptance_observation`: исходная цель запуска iOS сохраняется, позднее уточнение делает опциональным E2E; `inference`: общая мобильная компоновка ограничивает платформенные изменения | CAP-02, CAP-06, CAP-07 | Настоящий runner доходит до отображения стартового интерфейса без сбоя платформенной инициализации. Вход, Keychain restore и HLS относятся к D-07. Конфигурации Debug/Profile/Release согласованы с flavor; release-сборка и распространение iOS не заявляются |
| D-04 | Dev/prod изолируют Keychain и preferences; общая Keychain access group и синхронизация iCloud не включаются. Доступность защищённых записей — только на разблокированном устройстве | `inference`: продолжает принятую изоляцию аккаунтов и минимальный доступ к сессии, не требует совместного хранилища | CAP-03 | Настройки сверить с закреплённым plugin; детерминированные проверки обязательны, нативное подтверждение изоляции и восстановления входит в опциональный E2E по D-07. ## Неизвестное и границы

### Внешние зависимости и обработка

- EXT-01 — владелец окружения разработки: совместимость установленного Xcode, iPhone Simulator runtime и интеграции native packages ещё не подтверждена; обработка: исполнитель до обязательной iOS сборки/базового запуска проверяет среду. Отсутствие нужного компонента фиксирует как препятствие подтверждению CAP-02; Android gate от него не зависит. Установку или обновление проводит по процедуре настройки окружения.
- EXT-02 — AniStar/CDN и владелец тестового аккаунта: работа реального сайта и CDN с iOS для выбранного зеркала/IP ещё не подтверждена; обработка: после отдельного разрешения на live QA использовать выделенный аккаунт и безопасную передачу credentials. До этого результат обозначать «живой AniStar/CDN на iOS не проверен»; fixture-успехом его не подменять. В согласованном объёме live воспроизведение может добавить отметки истории аккаунта, что отражается до запуска.

- EXT-03 — владелец тестового окружения: доступность доверенной HTTPS fixture-среды для настоящих Keychain/AVFoundation и выбранного дополнительного iPad Simulator не подтверждена; обработка: проверять эти условия только перед явно выбранным iOS E2E или диагностикой iPad. При отсутствии записать конкретную причину невыполнения; обязательный gate не блокировать. Отказ доверия не обходить ATS/TLS-исключением. Fixture-среда и iPad runtime не являются условием базового iPhone-запуска.

- EXT-04 — GitHub и владелец доступа: возможность push и создания PR в целевом репозитории ещё не подтверждена; обработка: исполнитель перед публикацией проверяет remote, текущую ветку и права через доступный connector или CLI без вывода credentials. При отказе сохраняет локальный результат и описание PR, сообщает заблокированное действие и условие возобновления. Доступ не заменяется предположением об успехе.

### Исследование, ограничение по времени и результат

Полный native HTTPS-путь CAP-04 входит в опциональный iOS E2E. Только при его явном запуске исполнитель получает один рабочий день реализации и диагностики совместимости существующего video_player/AVFoundation. Проверяются HLS по URI с суффиксом `.mp4`, Referer у master/variant/segments, относительные и абсолютные media URI, Range/seek, переключение качества и серии. Отдельного обязательного прогона той же полной цепочки под названием исследования нет.

Результат выбранного исследования — воспроизводимое подтверждение текущего стека, конкретная найденная несовместимость либо явно неполное подтверждение с указанием недостающего доказательства. Несовместимость, требующая смены решения, возвращается в planning. Истечение времени не разрешает менять стек, ослаблять защиту или объявлять непроверенный сценарий рабочим. Пропуск исследования допустим по D-07; запись результата тогда — «iOS native HLS не проверен». Fakes не дают native-подтверждения.

### Риски

Главные риски — различия нативных транспортов Android/iOS, ошибочная общая область Keychain и конкурирующее управление idle timer. При пропуске iOS E2E эти границы остаются без нативного подтверждения, даже если сборка, базовый запуск и детерминированные проверки успешны. Найденная ошибка фиксируется независимо от обязательности проверки. Симулятор не подтверждает аппаратный декодер, жесты и блокировку физического iPhone; iPad с TV-профилем не подтверждает Apple TV и его пульт.

## Готовность и проверка

### Приёмка разработчиком и готовность

- CAP-01: конфигурация сборки и verifier ожидают новые ID и согласованные launcher labels; проверка подписи продолжает требовать прежний pin. Нет пути удаления старой установки или переноса её данных.
- CAP-02: зафиксирован запуск штатного генератора до настройки iOS и проверен его diff. Существующие Android/Dart/workspace и пользовательские изменения сохранены; у dev/prod согласованы схемы, bundle ID, точки входа и env-семантика по самодостаточному примеру iOS-конфигурации.
- CAP-03: детерминированные регрессии сохраняют границу входа при отказе записи/чтения/удаления, не допускают позднего восстановления прежнего аккаунта, не сохраняют пароль и не раскрывают credentials.
- CAP-04: регрессии сохраняют полный URI и заголовки, один общий автоматический refresh, позицию/паузу при смене качества, нулевую позицию новой серии и освобождение прежнего controller. Native-ошибки дают безопасный результат.
- CAP-05: переходы состояния однозначно вычисляют удержание; фон, пауза, ошибка, возврат и уничтожение экрана снимают его. Поздняя инициализация не запускает фоновое видео.
- CAP-06: iOS получает mobile-профиль без зависимости от ширины; действия доступны при экранной клавиатуре и увеличении текста. Явный TV-профиль ограничен диагностическим запуском, его компоновка следует ADR-0008 и действующим TV/motion-спецификациям. Изменённые взаимодействия покрыты соответствующими регрессиями; существующие Android TV/mobile-проверки проходят.
- CAP-07: `test:e2e:ios` предоставлен как публичная Melos-команда с документированным выбором цели и flavor, проверкой необходимых условий и отдельным результатом. Детерминированные tooling-регрессии подтверждают, что Android gate его не запускает и не требует iOS runtime; выбранный запуск не маскирует отсутствие среды или падение под успех. Документы различают обязательные проверки, опциональные сценарии и фактически полученные доказательства. Обновлены связанные продуктовые, архитектурные, сетевые, storage/mobile/playback и tooling-контракты без копирования истории прогонов.
- CAP-08: корневой `pubspec.yaml` содержит согласованную новую версию, workspace-версии сохранены; Android и iOS получают одинаковые базовые X.Y.Z/N через Flutter; Android dev сохраняет `versionNameSuffix -dev`. CHANGELOG сохраняет прошлые записи и описывает реализованные возможности без неподтверждённых заявлений. Руководство версий учитывает обе платформы.
- CAP-09: commit содержит итоговый проверенный объём изменения; фактический PR создан из рабочей ветки в `main` нужного репозитория и привязан к чату. Его описание сообщает новую версию, изменения, обязательные результаты и ограничения iOS-проверки. Отсутствующий доступ или неполная проверка отмечены как незавершённый шаг.

- CAP-10: значимые tooling-регрессии подтверждают одинаковый выбор JSON для CLI/IDE, создание prod из валидного шаблона только при отсутствии, сохранение локального значения при повторной подготовке и отказ до Flutter при повреждённом JSON/отсутствующем нужном файле. Проверяются существующие app-параметры, не только синтаксис JSON. Prod остаётся ignored и не попадает в staged diff; ни один обычный запуск не использует live credentials или `prod.example.json` напрямую.
- CAP-11: структура workspace профилей соответствует таблице: единый SDK, `program`/`flutterMode`/`toolArgs`, окружение процесса со значением `unsigned` и общий `preLaunchTask`. Регрессии проверяют отсутствие дублирующего `--target`, Flutter flags в `args` и зависимостей F5 от полного gate/E2E/live. Существующие Melos-задачи и применимые рекомендации сохранены; iOS E2E отмечен опциональным. Фактический F5 оценивается отдельно от структурной проверки.

Семантическая карта готова к утверждению; реализация начинается после утверждения и выбора следующего этапа. Подготовка iOS runner и общей логики не требует предварительного E2E. Обязательный результат этой итерации — реализация CAP-01–CAP-11: обновлённое приложение и версия, успешный Android gate, отдельная iOS сборка/базовый запуск, техническое ревью и итоговый PR. Выполнение iOS E2E и диагностики iPad не является условием его завершения. При их пропуске нельзя заявлять нативную совместимость полного iOS-сценария.

Обязательные проверки:

- Выполнить последовательный Android gate: `fvm dart run melos run check` → `fvm dart run melos run test:e2e` → `fvm dart run melos run build:android:prod:apk`. Полностью пройти существующие TV и mobile fixture-наборы на Android-устройствах/эмуляторах с настоящими native backend, включая вход/restore, каталог, HLS, lifecycle, пульт/сенсорное управление и возврат. Наборы не заменяют друг друга; у каждого отдельный результат.
- На Android проверить сосуществование старого и нового приложения, сохранность старых данных, независимость dev/prod и чистую новую сессию. Проверить ID, новую версию и прежний pin сертификата итогового APK. Отсутствующий ключ препятствует подписанной проверке; unsigned-сборка её не заменяет.
- На iPhone Simulator собрать, установить и базово запустить dev и prod в режиме debug с настоящим runner; подтвердить разные bundle ID, новую X.Y.Z/N из корневого pubspec в metadata обоих flavor, одновременную установку и отображение стартового интерфейса без сбоя платформенной инициализации. Допустимое состояние сетевой ошибки startup не подтверждает вход или доступность сайта. Эта проверка не включает вход в реальный аккаунт, Keychain restore, каталог или HLS.
- В доступной VS Code среде выполнить F5 для dev/prod на Android и выбранном iPhone Simulator в debug; подтвердить SDK, flavor, точку входа, env-файл и запуск стартового интерфейса. Наблюдать, что подготовка не перезаписывает локальный prod и не запускает E2E/live; debug/profile не читают production credentials даже при унаследованном production signing mode. Если IDE runtime недоступен, записать «VS Code F5 не проверен» с причиной; успешный CLI debug не выдавать за F5.
- После завершения проверок и ревью перед commit/push сверить итоговый diff, версию и CHANGELOG; после создания PR проверить репозиторий, `base=main`, исходную ветку и commit. Опубликовать фактическую ссылку и результаты; успешный push сам по себе не подтверждает создание PR.

Опциональные проверки, предоставляемые планируемой командой `fvm dart run melos run test:e2e:ios` с документированным выбором симулятора и flavor:

- На iPhone Simulator для dev/prod через доверенный HTTPS fixture и настоящий Keychain проверить неверный пароль → вход → перезапуск → восстановление без второго POST → истечение сессии → выход → новый запуск. После входа в один flavor второй остаётся независимым; preferences также изолированы, смена origin не переносит cookies.
- На настоящем AVFoundation пройти полный HLS-путь исследования, 360p/720p, pause/resume, seek, смену качества с сохранением позиции/паузы и смену серии с нуля. Проверить отказ, ограниченный refresh и отсутствие site cookies на CDN-границе.
- Проверить платформенное состояние idle timer при play/pause/buffering/completed/error, смене источника, фоне, возврате, Back и dispose.
