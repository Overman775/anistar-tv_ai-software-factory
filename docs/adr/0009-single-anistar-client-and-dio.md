# ADR-0009: Единый AniStarClient и HTTP-транспорт Dio

- **Статус:** Accepted
- **Дата:** 2026-10-11
- **Уточняет:** [0004: Riverpod для DI](0004-use-riverpod-for-app-di.md), [0005: Логирование](0005-centralize-runtime-logging.md), [0007: Границы инфраструктуры](0007-neutral-core-and-infrastructure.md).

## Контекст

Репозитории получали AnistarSource для каталога, карточек и плейлистов, а AuthRepository — отдельный AnistarAuthService. Общий Dio и cookie-сессия уже существовали, но единого контракта клиента не было. Это позволяло feature data зависеть от деталей HTML и авторизации. Проверка зеркал создавала Dio вне общей фабрики, а networking также содержал неиспользуемый клиент на package:http.

## Решение

Уточнение от 2026-10-12: [ADR-0010](0010-normalized-anistar-contract.md) разделяет общий DTO API и HTML-библиотеку; текущая реализация называется HtmlAnistarClient. Историческое описание ниже сохраняет контекст принятия ADR.

Цепочка получения данных: UI → BLoC/controller → domain repository interface → repository implementation → AnistarClient → Dio и внутренние парсеры. Для экранов с локальным async lifecycle роль controller выполняет State.

- AnistarClient — общий контракт инфраструктуры AniStar. Он предоставляет авторизацию, события истечения сессии, каталог, фильтры, карточки, избранное, плейлисты и отметки просмотра.
- DioAnistarClient реализует контракт. Он координирует загрузку HTML, charset, DOM/JSON5, авторизацию и общую cookie-сессию. AnistarSource и AnistarAuthService остаются внутренними деталями пакета и не экспортируются в основной API.
- Репозитории принимают AnistarClient конструктором. Они преобразуют DTO сайта в domain-модели и исключения в Result/Failure. Репозитории не импортируют Dio, HTML-парсеры или Riverpod. Клиент возвращает DTO либо бросает исключение; Result создаётся на границе репозитория один раз.
- Riverpod остаётся единственным DI-контейнером. anistarClientProvider создаёт один клиент в корневом ProviderScope и передаёт ему Dio, AnistarSession и проверку зеркала. app_container передаёт этот же provider всем сетевым репозиториям. Клиент и репозитории не ищут зависимости через Ref, BuildContext или статический singleton.
- «Глобальный» означает общий для активного приложения и origin. При смене зеркала Riverpod пересоздаёт Dio, клиент, сессию и зависимые репозитории. Cookies и пароль не переносятся на новый origin. Каждый тестовый контейнер изолирован.
- DioClient в networking — единая фабрика транспорта с таймаутами, ограниченным retry и общим logger. Session/header interceptors устанавливаются перед logging interceptor. Неиспользуемый транспорт package:http удалён.
- Один общий Dio обслуживает запросы авторизованного клиента. Единственное дополнительное соединение Dart-кода — probe зеркал из той же фабрики, без session interceptor, cookies, redirect и retry. Оно необходимо, чтобы проверка доступности не переносила авторизацию между доменами и не запускала рекурсивное восстановление зеркала.
- Networking владеет lifecycle общего Dio через ref.onDispose; провайдер сессии закрывает её очередь и stream. Клиент использует переданные зависимости и не закрывает их повторно. AnistarMirrorManager закрывает свой probe.
- Debug/profile выводит все уровни в консоль и файл; release — только error/fatal. Необработанные ошибки Flutter, PlatformDispatcher и guarded zone имеют уровень fatal и маркер UNHANDLED. Сетевые сообщения скрывают credentials, cookies, query, тела и подписанные paths. Firebase и внешняя аналитика не подключены.

## Последствия и ограничения

Все сетевые features используют одну точку доступа к данным сайта и одну cookie-сессию. Изменения HTML и протокола входа остаются внутри инфраструктуры; клиент можно заменить через Riverpod override без изменения репозиториев и UI.

Единый клиент не объединяет domain-репозитории разных features и не добавляет общий кеш. Native video_player загружает HLS своим транспортом: Dio получает страницы и плейлисты, а не видеопоток. Чистые парсеры доступны через parsing.dart для инфраструктурных тестов и не используются feature data.

Проверки: architecture-тест запрещает transport/parser/DI imports в feature data; DI-тест подтверждает общую сессию входа и каталога, очистку cookies после выхода и закрытие транспорта; mirror-тест подтверждает замену клиента и изоляцию cookies при смене origin. Существующие fixture-тесты проверяют операции через AnistarClient.

Дополнительные регрессии проверяют DNS/connection failure и восстановление после cooldown, отсутствие POST при отказе проверки зеркала, повторный вход после восстановления сети, безопасную обработку неожиданной ошибки проверки и событие expiry на границе клиента/репозитория. Отдельные явно запускаемые host/Android smoke проверяют реальную сеть и вход без записи в избранное и историю. Команды и диагностика DNS: [разработка и тестирование](../05_development_and_testing.md#9-проверка-с-живым-аккаунтом).
