# Прямая работа AniStar из Flutter

На 9 октября 2026 года Android и iOS могут получать каталог, карточки и серии, воспроизводить HLS 360p/720p и скачивать видео напрямую с `https://v30.astar.bz`, без отдельного сервера `anistar_parser`. Это проверено в отдельном Flutter-приложении с теми же версиями видеоплагинов, что использует проект. Основное приложение пока продолжает работать через parser API.

Для обычного Flutter Web полностью убрать посредника сейчас нельзя: браузер блокирует чтение каталога и страницы серий из-за CORS. Подписанный 720p HLS при этом воспроизводится напрямую через hls.js. Старый 360p и MP4 отклоняют Referer нашего Web-приложения.

## Условия проверки

Проверялось аниме `10938`, «Пожалуйста, простите моих младших братьев», серии 1 и 2. В списке доступны 14 серий. Запросы Dart выполнялись через `package:http`, без cookies, исполнения JavaScript и CAPTCHA. Результат относится к текущему подключению и зеркалу; он не гарантирует такое же поведение на других IP или после смены защиты сайта.

Среда: Flutter 3.44.0, Dart 3.12.0, `video_player` 2.13.0, Android/AVFoundation implementations 2.11.0. Android — ARM64 emulator API 36; iOS — iPhone 17 Pro simulator с iOS 26.5. В браузере проверялся Chrome и hls.js 1.7.3. SDK проекта 3.44.2 на этой машине содержит Dart для x86_64 и не запускается на arm64, поэтому эксперимент использовал уже установленный совместимый SDK 3.44.0.

Физические Android TV и iPhone, release-сборки, фоновая загрузка и непрерывный просмотр всей серии в native-плеере не проверялись. В репозитории сейчас есть только Android platform project; для iOS и Web ещё нужно добавить соответствующие сборочные проекты.

## Прямые запросы и разбор данных

| Проверка | Результат |
| --- | --- |
| `/anime/` | `200`, Windows-1251; 9 карточек после исключения рекламы `9493` |
| `/anime/page/2/` | `200`, Windows-1251; 10 карточек |
| Карточка `10938` | `200`; название, описание, год, жанры, озвучка и сведения о сериях прочитаны Dart-клиентом |
| `/test/player2/videoas_p2p_new.php?id=10938` | `200`, UTF-8; разобраны серии 1–14 |
| Источники каждой серии | `files`, `files_mp4`, `files_as`, качества 360/720 |

Каталог desktop-разметки использует `.news`, `.title_left a`, `img[itemprop="image"]`; название карточки — `h1[itemprop="name"]`, описание — `.descripts`, метаданные — `ul.head`. `playlst` извлекается с учётом строк, комментариев и вложенных массивов, затем разбирается как JSON5. JavaScript страницы не исполняется. Номер серии и качество привязаны к своим объектам; порядок URL не используется.

Кодировку нужно выбирать по `Content-Type` и декодировать `bodyBytes`. `response.body` из HTTP-клиента не является достаточным решением для Windows-1251. Пагинацию нужно получать из HTML: на проверенной странице указан последний номер 690, поэтому серверную константу количества страниц переносить в клиент нельзя.

## Воспроизведение Android и iOS

На обеих платформах прошли инициализация, старт, перемотка на 120-ю секунду и продолжение воспроизведения для серий 1 и 2 в 360p и 720p. Контроллер предыдущей серии освобождался перед созданием следующего. Плееры сообщили разрешения 640×360 и 1280×720; длительность первой серии — примерно 1454,85 секунды. Это проверка переключения источника в тестовом приложении, а не готовый интерфейс смены серии в основном приложении.

Прямые MP4 360p и 720p также запустились и перемотались на обеих платформах. Контрольный HLS 360p без Referer завершился ошибкой; сетевой запрос к сегменту без него вернул `403`, с ним — `206`.

Для HLS нужно создавать контроллер так:

```dart
VideoPlayerController.networkUrl(
  source.uri,
  formatHint: VideoFormat.hls,
  httpHeaders: {
    'Referer': 'https://v30.astar.bz/test/player2/videoas_p2p_new.php?id=10938',
  },
);
```

`formatHint` действует на Android. Контрольный запуск нового 720p с правильным Referer, но без `formatHint`, завершился `ExoPlaybackException: Source error`. В iOS проверенный 720p распознаётся AVFoundation по ответу сервера, несмотря на окончание пути `.mp4`. API конструктора и Android-ограничение описаны в [документации video_player](https://pub.dev/documentation/video_player/latest/video_player/VideoPlayerController/VideoPlayerController.networkUrl.html).

В Android implementation 2.11.0 заголовки устанавливаются на общую `DefaultHttpDataSource.Factory`; в iOS implementation 2.11.0 передаются в AVURLAsset. Положительный тест 360p и отрицательный тест без Referer подтверждают, что заголовок доходит до защищённой цепочки загрузки в проверенном потоке. Отдельных вложенных master playlists в этом образце нет; их передачу следует включить в проверки при расширении набора источников.

Новый 720p возвращает `application/vnd.apple.mpegurl` и `#EXTM3U`. У первой серии 291 сегмент, у второй — 290. Ссылки разрешаются относительно URL манифеста и ведут на `sfv.an-media.org` и `ip381253095.ahcdn.com`. Конкретный ahcdn-хост отличается от исходного исследования: фиксировать один hostname нельзя.

## Скачивание и офлайн

`files_mp4` доступен: `sfhd.an-media.org` вернул `206`, `video/mp4`, сигнатуру `ftyp` и корректный `Content-Range`. Размер первой серии — 81 788 173 байта в 360p и 159 718 649 байт в 720p.

Полный MP4 360p скачан на Android и iOS: получено ровно 81 788 173 байта. Локальный MP4 запустился и перемотался на 120-ю секунду на обеих платформах. Для первоначальной реализации загрузок MP4 — наиболее простой подтверждённый путь: HTTP-поток сохраняется в файл и воспроизводится через `VideoPlayerController.file`.

Полная HLS-серия 360p скачана Dart-инструментом на компьютер: 146 сегментов, 88 520 176 байт. Плейлист переписан на локальные имена файлов. FFmpeg декодировал всю серию без ошибок с разрешёнными только `file,crypto,data`; HTTP/HTTPS были запрещены. Размер HLS отличается от MP4 из-за упаковки и служебных данных.

В native-приложениях дополнительно сохранён 30-секундный HLS-фрагмент: 3 сегмента, 1 721 704 байта. Android воспроизводит локальный `.m3u8` через `VideoPlayerController.file`, включая перемотку. На iOS такой контроллер не завершил инициализацию за 40 секунд. Тот же локальный плейлист и сегменты успешно воспроизвелись на обеих платформах через небольшой `HttpServer`, работающий внутри приложения на `127.0.0.1`: старт и перемотка на 15-ю секунду, 4 обращения к локальному серверу, 0 запросов upstream во время воспроизведения. Это компонент на устройстве; отдельный удалённый сервер ему не нужен. Полный HLS-файл в native-плеерах и офлайн 720p отдельно не проверялись.

Обобщённый HLS-downloader должен сохранять выбранные дочерние плейлисты, сегменты, ключи и initialization segments, учитывать byte ranges и discontinuities, переписывать все URI и фиксировать завершённость загрузки. Экспериментальный downloader поддерживает только проверенный полный VOD с незашифрованными TS-сегментами. Для устойчивых фоновых загрузок нужны компоненты на устройстве: например, [Media3 DownloadService/DownloadManager на Android](https://developer.android.com/media/media3/exoplayer/downloading-media) и [AVAssetDownloadURLSession на iOS](https://developer.apple.com/documentation/avfoundation/avassetdownloadurlsession). Внешний сервер для этого не требуется; интеграция этих API отдельно не проверялась.

## Истечение ссылок и повторные попытки

Подписанный URL сохраняется целиком. В эксперименте Dart сохранил `+`, запятые и структуру пути; тест специально проверяет эту особенность. Самостоятельно генерировать подпись не нужно. Значение `end` находилось примерно на сутки впереди времени получения страницы.

Неверный `key` и изменённый `end=1` вызывают отказ. Повторное получение страницы плеера и выбор той же серии/качества восстановили доступ к HLS с `200`; выполнено ровно одно обновление. Unit-тест постоянного `403` подтверждает предел: два media-запроса и один запрос страницы, без бесконечного цикла.

Естественное истечение неизменённой ссылки через сутки не проверялось. Изменение `end` также нарушает подпись, поэтому эксперимент подтверждает восстановление после отказа CDN, но не устанавливает точную семантику срока действия. Для клиента достаточно обрабатывать отказ с одним обновлением источника; после повторной ошибки показывать ошибку. Перед пересозданием контроллера нужно сохранять текущую позицию и возвращаться к ней.

## Flutter Web

Проверка выполнялась со страницы `http://127.0.0.1:8765` в обычном Chrome, с включёнными ограничениями браузера. Сравнение запросов с `Origin` подтвердило причины:

| Ресурс | CORS и Range | Практический результат |
| --- | --- | --- |
| Каталог и страница плеера AniStar | Нет `Access-Control-Allow-Origin` | `fetch` завершается `TypeError: Failed to fetch` |
| Каталог с `mode: no-cors` | Ответ opaque | Статус 0, читаемое тело отсутствует; HTML разобрать нельзя |
| 360p `sf2.an-media.org` | CORS разрешает Origin приложения; Range поддерживается | `403` с браузерным Referer |
| MP4 `sfhd.an-media.org` | Ответ доступен браузеру | `403` с браузерным Referer |
| 720p `sfv.an-media.org` | `Access-Control-Allow-Origin: *`, Range даёт `206` | Манифест и сегменты доступны |
| 720p `*.ahcdn.com` | `Access-Control-Allow-Origin: *`, Range даёт `206` | Сегменты доступны |

В 720p JavaScript прочитал 4096 байт TS с `206`. `Content-Range` браузеру не виден, поскольку CDN не выставляет соответствующий `Access-Control-Expose-Headers`; это не означает отсутствия поддержки Range.

Попытка установить `Referer` через `headers`, а также `referrer` с чужим AniStar URL, не дала нужного заголовка и не устранила `403`. Браузер управляет этим заголовком; произвольную подмену не предоставляет. См. [Referer](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referer), [Range](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Range) и [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

hls.js 1.7.3 воспроизвёл прямой 720p первой и второй серии: 1280×720, старт с продвижением времени и перемотка с продолжением после 122-й секунды. Это обычная браузерная проверка с заранее полученными Dart-инструментом URL, а не готовая Flutter Web-сборка. Для Chrome потребуется HLS-интеграция через MSE, например [hls.js](https://hlsjs.video-dev.org/api-docs/hls.js.hls); текущая Web implementation `video_player` просто задаёт источник HTMLVideoElement и не добавляет HTTP-заголовки или hls.js.

При нынешних ответах сайта Web всё равно требует компонент с доступом к HTML вне браузерного CORS. Можно оставить небольшой API для каталога/карточек/серий и выдачи свежих URL, а 720p доставлять напрямую с CDN. Для сохранения собственного Web-плеера 360p и MP4 нужен прокси, выставляющий подходящий Referer. Встраивание штатного плеера AniStar не проверялось и не решает чтение каталога своим клиентом.

## Изменения в основном клиенте

1. Добавить `DirectAnistarDataSource` и реализации существующих `CatalogRepository`, `AnimeRepository`, `PlaybackRepository`, получающие HTML. Подключить их через `app_providers.dart`. Domain-модели и основную структуру экранов можно сохранить.
2. Отделить адрес зеркала от `ANISTAR_API_URL`. Сохранять стабильные ID/slug, поддержать смену зеркала и ошибку при защитной странице вместо пустого успешного результата.
3. Добавить DOM-разбор HTML, декодер Windows-1251 и безопасный разбор JSON5. Фильтровать рекламу по ID `9493`; пагинацию читать из страницы.
4. Расширить `PlaybackSession`: URL источника, формат, заголовки, доступные качества и необязательное время истечения. `tokenTtl` сейчас относится к серверным proxy-токенам и не равен сроку upstream URL. Сессию и `files_mp4` лучше хранить как разные типы источников.
5. В `PlayerScreen` передавать `httpHeaders` и `VideoFormat.hls`. Определять HLS по группе источников и проверять MIME/`#EXTM3U`; не отбрасывать `.mp4` из `files`. Для настоящего MP4 использовать соответствующий формат.
6. Добавить однократное обновление страницы после отказа, восстановление позиции, отмену устаревших запросов и освобождение предыдущего контроллера при смене серии/качества.
7. Добавить менеджер загрузок: streaming в файл, progress/cancel, докачка с Range, проверка размера и атомарное завершение. Для HLS нужен отдельный downloader и стратегия локального воспроизведения.
8. Для Web предусмотреть отдельную реализацию доступа к метаданным и HLS-плеера. При нынешнем CORS полная замена API прямым HTTP невозможна внутри обычного браузерного приложения.

У текущего parser обнаружены две независимые несовместимости с новым 720p: фильтр `.m3u8` в `astar/services/video/playlist.py` отбрасывает этот источник, а `_RE_CDN_HOST = ^sf\d+\.an-media\.org$` в `astar/services/video/service.py` не допускает `sfv` и `*.ahcdn.com`. Поэтому даже временное сохранение parser требует корректировки определения формата и проверки CDN-хостов. В этом задании parser не изменялся.

## Воспроизводимость

Исходники эксперимента находятся в `tool/direct_probe`. Подробные ответы и результаты плееров без подписанных URL сохранены в [JSON протоколе](anistar-direct-2026-10-09.json).

```bash
cd tool/direct_probe
dart pub get
dart test
dart analyze lib bin test
dart run bin/probe.dart /tmp/anistar-direct-probe
dart run bin/download_hls.dart /tmp/anistar-direct-probe/offline-hls
```

Для браузера скопировать `browser_probe.html` и `browser_playback.html` в временный output-каталог, установить туда `hls.js@1.7.3` и запустить статический сервер на `127.0.0.1:8765`. `private_urls.json` содержит временные upstream-ссылки и остаётся в этом каталоге.

Для native создать отдельный Flutter-проект Android/iOS и использовать `flutter_runner/lib/main.dart` с зависимостями из `flutter_runner/pubspec.yaml`; path dependency должна указывать на `tool/direct_probe`. Обычный запуск проверяет сеть и online playback; `--dart-define=OFFLINE_ONLY=true` проверяет скачивание и офлайн, `--dart-define=FORMAT_HINT_ONLY=true` — контрольный запуск 720p без явного формата. В SDK/Xcode данной машины для временного iOS-проекта понадобился deployment target 15.0. Android-вариант локального HTTP-сервера разрешает cleartext только для `127.0.0.1` через network security config. На iOS использован стандартный Info.plist временного Flutter-проекта без дополнительных ATS-исключений.

В основной production-код изменения не вносились. Шесть проверок парсинга, кодировок, привязки качеств, разрешения URI и ограничения повторов прошли; Dart-инструмент и Flutter runner проходят статический анализ.
