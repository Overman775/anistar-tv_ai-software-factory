## 1. Контекст и ожидаемый результат

Избранное и обновление выдачи сохраняют подтверждённый статус и контекст. Задача реализует соответствующую часть утверждённого плана; демонстрационные аккаунт/видео/задержки/локальные данные не становятся логикой приложения.

### Организация выполнения

Эта задача входит в крупный пакет B; внутренние задачи не запускают отдельную полную цепочку. Developer последовательно завершает весь пакет, выполняет Static Gate и фиксирует состав/хеши, затем передаёт весь результат TestWriter → DevReviewer → исправления по фабрике. Developer пишет рабочий код; TestWriter — тесты; документация через DocWriter/владельца окна. До передачи могут идти локальные проверки разработчика, но новый пакетный test-report не заявляется заранее. После фиксации production-код пакета не изменяется до возврата из тестирования/ревью; новая правка повторяет затронутые gates.

## 2. Что входит в задачу (`implemented`)

1. Избранное использует ту же сетку/инспектор/состояния. Сердце на общей закладке видно только при подтверждённом true на главной/фильтре; в самом избранном скрыто, неизвестный статус не превращается в false.
2. Удержание карточки/мобильное действие открывает общий контейнер с существующим чтением статуса. Сохранить один сериализованный mutation, серверное подтверждение, отсутствие запроса изменения при том же подтверждённом статусе, безопасную ошибку и перечитывание статуса. Закрытие панели не отменяет уже отправленный сайт-запрос.
3. Подтверждённый результат согласует кнопки/выдачи. После удаления последнего избранного TV фокус возвращается меню; исчезнувший объект не оставляет невидимую цель. Смена аккаунта/origin не принимает старый результат.
4. Mobile pull-to-refresh от начала короткого/пустого/ошибочного списка ждёт сеть и исключает More. Старые карточки сохраняются до успеха; ошибка не теряет страницу/hasMore, поздний refresh не стирает более новое подтверждённое изменение избранного.

## 3. Что отложено (`deferred`)

- Нет временно отложенного обязательного поведения внутри результата задачи. Остальные задачи эпика — отдельные результаты, не скрытые заглушки. Эпик нельзя объявлять завершённым до выполнения всех обязательных задач.

## 4. Архитектурный контекст

- **Область записи:** `lib/packages/features/favorites/`; `lib/packages/features/catalog/` — кроме navigation rail.
- **Переиспользование и ограничения:** Сохранить Clean Architecture: Presentation использует domain-контракты; Data преобразует публичные DTO и возвращает Result/Failure через BaseRepository. Riverpod — DI, BLoC — экранное состояние, App — маршруты. Без private src-импортов, dynamic, print, логирования HTML/cookies/credentials/signedURL; generated не менять вручную. UI Kit не знает feature-модели/предметные запросы/маршруты; загрузка изображения AppNetworkImage разрешена.
- **Критические решения:** D-01, D-03, D-06, D-09, D-13; общие D-14/D-15: goldens разрешены без повторного вопроса, commit/push только последним действием всего редизайна.
- **Подтверждённые факты и внешние условия:** EXT-01 не блокирует эту самостоятельную работу. Опоры текущего устройства: публичные контракты применимого пакета и существующие точки входа, перечисленные в утверждённом плане; точные файлы уточняются в execution brief без новых продуктовых решений.

**Границы записи:** пакет A владеет UI Kit, home, auth, common, log_viewer, App/Runner и navigation rail; пакет B — catalog (кроме rail), anime, favorites, watch_history и изменениями протокола/DTO anistar; пакет C — player. Общие файлы и документы изменяет только назначенный владелец в последовательном окне. Не откатывать чужие правки. Запрос на изменение вне своей области передаётся координатору.

## 5. Как проверить и принять

- **Проверяемый результат после PR:** Избранное и обновление выдачи сохраняют подтверждённый статус и контекст.

- [ ] Проверить true/false/unknown и отсутствие сердца в избранном; статус меняется только после подтверждения.
- [ ] Проверить success/no-op/failure/retry/busy, закрытие во время операции и смену сессии.
- [ ] Проверить refresh против pagination/mutation, короткий список и ошибка с сохранением данных, фокус после последнего удаления.
- [ ] Применимые тесты, эталоны и правила архитектуры проходят на зафиксированном пакете. TestWriter сохраняет команды/результаты и tested file hashes. Все затронутые goldens можно генерировать без вопроса пользователю; PNG/diff просматриваются, затем выполняется сравнение.
- [ ] Проверки Developer/Static Gate → TestWriter → DevReviewer идут по Factory Implement; Flutter/Gradle/codegen/общие gates запускаются последовательно в общем командном слоте. На время check/E2E/APK и генерации координатор замораживает весь проверяемый workspace и фиксирует общий снимок/хеши; для точечных тестов фиксируются пакет и потребляемые общие зависимости. DevReviewer выполняет только проверку формата и анализ без изменения production. Общие gates не дублируются после каждой внутренней задачи.

### Проверки QA после PR

- [ ] Ручной свайп/semantic tap, удержание физического OK и возврат из панели; fixture другого клиента.
- [ ] Реальные устройство/сеть/native fixture и пропуски отражены отдельно; offline widget/golden не выдаются за live или аппаратный TV.
