# Рефакторинг приложения, UI Kit и тестового tooling

## Зачем

Упростить сопровождение AniStar TV: убрать неиспользуемые режимы экранов,
лишние представления состояния и повторяющиеся правила; закрепить границы
UI Kit; сделать запуск и результаты проверок удобными для ИИ.

Документ объединяет весь аудит чата «Найти направления для рефакторинга»
от 24 октября 2026 года, включая уточнение пользователя о полном удалении
Inter и переданное замечание из ретроспективы о выборочном E2E.
Исходники проверялись на `11135ec`. Выводы основаны на чтении кода, мест
вызова, тестов, конфигурации и справки установленных CLI. Прогоны тестов,
сборки и измерения производительности в рамках аудита не выполнялись.
Сводные результаты DCM без детализации по лицензии не использованы как
доказательство дефектов.

Это расширенный Intent с материалами для передачи работы другому ИИ.
Он фиксирует желаемый результат и варианты реализации, а не утверждает,
что изменения уже внесены или что все предложенные API окончательно выбраны.
Перед реализацией сверить места вызова с текущей веткой: после даты аудита
они могли измениться. Уже реализованные пункты отметить со ссылкой на
проверяемое изменение, а не выполнять повторно.

## Чего хочу

Каждый пункт ниже имеет постоянный ID, исходные файлы, предлагаемое действие
и проверяемый результат. Обработать все ID: реализовать, подтвердить уже
сделанное либо явно обосновать отсрочку. Не терять отложенные предложения
и не превращать их автоматически в обязательную реализацию.

| Область | Пункты | Ожидаемый результат |
| --- | --- | --- |
| Приложение и инфраструктура | C01–C11 | Один действующий путь навигации и состояния, явные правила, меньше повторов |
| UI Kit и presentation | U01–U10 | Общие визуальные примитивы, согласованная геометрия и типографика, удалённый Inter |
| Тесты и инструменты | T01–T07 | Выборочные запуски, общая подготовка, краткая консоль и полные диагностические артефакты |
| Пересмотренные идеи | D01–D04 | Сохранены причины отсрочки; нет ненужной перестройки архитектуры |

### C01. Удалить самостоятельную оболочку CatalogScreen

**Основание:** все production-вызовы [CatalogScreen](../../lib/packages/features/catalog/presentation/screens/catalog_screen.dart)

со своим меню, Back, затемнением, переключением разделов и focus nodes;
production-навигацией уже владеет `TvRouteShell`.

**Направление:** удалить неиспользуемую оболочку и её параметры. Оставить
каталогу содержимое, сортировку, загрузку и фокус карточек. Тесты самостоятельного
режима перевести на реально используемую композицию приложения.

**Проверка:** меню, Back, возврат фокуса из карточки, пустое избранное,
TV/mobile и golden-сравнение. Риск средний; ожидаемое сокращение большое.

### C06. Собрать правила поиска и явно различать ошибки

**Основание:** [SearchBloc](../../lib/packages/features/search/presentation/search_bloc.dart),
[экран](../../lib/packages/features/search/presentation/search_screen.dart) и
[история](../../lib/packages/features/search/data/local_search_history_repository.dart)
повторяют ограничения длины и истории. Экран повторно вычисляет длину запроса,
чтобы отличить ошибку валидации от другой ошибки.
[AnistarSearchSource](../../infrastructure/anistar/lib/src/anistar_search_source.dart)
считает `runes.length`, feature — `length`; для части Unicode результат различается.

**Направление:** общие правила внутри Search и явная причина ошибки в состоянии.
Выбор единицы длины согласовать с контрактом поиска и upstream; не менять
Unicode-поведение незаметно под видом механического рефакторинга. Сохранить
проверки входа в адаптере и границу infrastructure → domain: инфраструктура
не должна импортировать feature для доступа к константе.

**Проверка:** пустой ввод, границы 4/120, Unicode, нормализация и лимит истории,
отдельное отображение сетевой ошибки. Риск средний.

### U01. Полностью удалить Inter, включая ассеты и лицензию

Это прямое уточнение пользователя, а не необязательная рекомендация.
В [pubspec UI Kit](../../lib/packages/ui_kit/pubspec.yaml) объявлены три
начертания Inter; действующая тема и тестовая загрузка используют Manrope.

относящийся к нему `LICENSE.txt` вместе с регистрацией лицензии.
Сохранить Manrope, `Manrope-OFL.txt`, лицензию иконок и остальные ресурсы.
Обновить ссылки FlutterGen штатной генерацией, без ручной правки generated-кода.

Проверка: нет Inter в действующих исходниках, manifest и generated-ресурсах;
Manrope отображается в TV/mobile и golden-сравнение не изменилось.

1,78 МиБ исходных Inter-файлов; экономию APK измерять отдельно.
Новый `app_fonts.dart` не требуется: типизированный `FontFamily` уже генерируется.

### T01. Единый способ полного и выборочного запуска

**Основание:** [test:unit/test:goldens](../../pubspec.yaml) используют Melos
`steps`. Установленный и закреплённый в lockfile Melos 7.8.1 передаёт
`extraArgs` в обычный `run`, но не в `_runMultipleScripts` для `steps`.
Добавление пути или `--plain-name` к нынешнему public alias не обеспечивает
передачу фильтра конечному Flutter-процессу.

Нужен тонкий общий runner с явным разбором и передачей аргументов; Melos
остаётся источником публичных команд. Возможен отдельный обычный `run`
для выборочного запуска. Конкретные имена новых команд пока не закреплены.
Подготовку SDK/dependencies выполнять один раз, сохранив lockfile и seed.
Не копировать всю последовательность подготовки в каждый новый wrapper.

Требования к интерфейсу:

- Полный набор, один файл и фильтр имени поддерживаются для host-тестов и golden comparison.
- Поддержать `--plain-name` как поиск подстроки; он может выбрать несколько тестов. Для точного выбора предусмотреть однозначный интерфейс либо документированный anchored `--name` с корректным экранированием.
- Показывать реально выполненные тесты в отчёте. Нулевое совпадение не считается OK.
- Сохранять возможность раздельного запуска unit/widget и golden. Сейчас `test:unit` фактически выполняет все тесты без тега `golden`, включая widget; описание команды должно это объяснять.
- `test:coverage` и `test:unit` сейчас запускают один и тот же набор с coverage. Не выдавать их за независимые проверки и не запускать последовательно без причины.
- Golden comparison и `--update-goldens` остаются разными действиями; обычный runner не обновляет эталоны автоматически.

Если нужны отдельные выборки unit и widget, определить устойчивое правило
тегов/путей и проверить инвентарь. Наличие или отсутствие строки `testWidgets`
само по себе не является надёжной классификацией всех тестов.

### T02. Краткая консоль и структурированные артефакты

**Желаемый контракт:** успешный запуск выдаёт краткий `OK` с областью проверки,
счётчиками и путём к отчёту. Неуспешный — `FAIL`, этап/тест, диагностическое
сообщение, полезный stack trace и путь к полному логу. Без анимации прогресса,
ANSI-перерисовок, списка успешных тестов и повторов команд на каждом уровне.
При длительном запуске допустима редкая короткая отметка живого процесса.

`machine`/`json` — формат для программного разбора, а не способ уменьшить
объём текста в контексте ИИ. События сохранять в файл; агенту по умолчанию
давать итог и ошибки. JSONL может содержать перемешанные события и ошибку
после успешного `testDone`; учитывать это при агрегации согласно
[протоколу Dart test](https://github.com/dart-lang/test/blob/master/pkgs/test/doc/json_reporter.md).

| Инструмент | Подход, проверенный по справке установленной версии |
| --- | --- |
| Flutter unit/widget/golden | `--reporter=failures-only` и дополнительный `--file-reporter=json:<path>`; общий runner формирует summary |
| Flutter native E2E | Тот же разделённый вывод плюс отдельное сохранение build/preflight/runtime-логов |
| Flutter analyze | `--no-congratulate --no-preamble`; сохранить строгие fatal-параметры |
| Dart analyze | Поддерживает `--format=json` и `--format=machine`; замена текущего Flutter analyze допустима лишь после сверки охвата, диагностик и exit codes |
| DCM analyze | `--concise --no-congratulate` для консоли либо JSON-отчёт с кратким итогом; сохранить `--fatal-style --fatal-warnings` |
| Python unittest | `-q` и общий итог; traceback и ошибки не скрывать |

У `flutter analyze` в проверенной справке нет `--machine`; не добавлять
несуществующий флаг по аналогии с `flutter test` или `dart analyze`.
Под «только ошибки» понимаются все диагностики, из-за которых gate падает,
включая fatal warnings/info/style. Не менять severity и exit codes ради тишины.

В [quality:unit/quality:goldens](../../pubspec.yaml) reporter сейчас не задан.
В [e2e.sh](../../scripts/e2e.sh) используется `expanded`, а общий `tee`
зеркалирует весь вывод. Одной смены reporter недостаточно: нужно охватить
SDK/build/preflight, Python tooling и баннеры вложенных Melos-команд.
Не фильтровать строки поиском слова error и не терять exit code в pipeline.
Для отладки предусмотреть явный подробный режим и доступ к полному файлу.

Переиспользовать пригодную часть [e2e_report.py](../../tool/e2e/e2e_report.py),
где уже есть JSONL → summary/JUnit и проверки незавершённых/нулевых запусков.
Общий парсер не должен делать host-тесты зависимыми от emulator tooling.
Не создавать вторую независимую реализацию протокола без необходимости.

Минимальные поля отчёта: schema version, suite/platform, `scope=full|filtered`,
селектор, seed, длительность, process exit code, итоговый статус, этап сбоя,
passed/failed/skipped, имена фактически завершённых тестов и пути артефактов.
Для E2E сохранить device/AVD; для golden-ошибок указывать actual/expected/diff.
Для каждого запуска отдельный каталог, чтобы старый PASS не подменял новый.

а не причина повторно запустить уже работающий E2E.

- Поведение пользователя, маршруты, TV-focus/Back, mobile-жесты, accessibility, reduced motion и увеличенный текст. Изменения взаимодействия сверять с [ADR-0008](../adr/0008-youtube-tv-interaction-reference.md) и его спецификациями; визуальную систему — с [spec 11](../specs/11_visual_system.md).

## Как продолжить работу

Сначала сделать выборочный запуск и честный краткий отчёт T01–T03/T07:
это упростит проверку следующих изменений. Независимая небольшая задача — U01.
Далее C01–C03 и простые удаления C10/U08/U10; затем подписи/типографика/геометрия
U02/U06/U07, согласуя их общие входы. Остальные локальные изменения выполнять
отдельными проверяемыми шагами. Порядок рекомендательный, не набор уже
согласованных задач или оценок сроков.

Для каждого выбранного шага: подтвердить актуальную проблему и потребителей,
зафиксировать сохраняемое поведение, внести минимальное изменение, выполнить
подходящие регрессии и указать фактический результат. При чистом рефакторинге
не маскировать изменившийся golden массовым обновлением. Для семантического
расхождения, например Unicode в C06, отдельно сформулировать ожидаемый контракт.

Финальный отчёт реализации должен перечислить обработанные ID, намеренно
отложенные пункты и причины, запущенные команды с областью full/filtered,
exit codes и пути к артефактам. Непроведённые проверки обозначать прямо.
