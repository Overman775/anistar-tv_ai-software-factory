# Примеры проектных гейтов

Подключения — в [project.example.yaml](../../project.example.yaml).
Файлы: [авторы](roles/authors.yaml), [финальная проверка](roles/judge.yaml),
[ревью](skills/code-review.yaml).

Это комплект файлов: при переносе сохраняйте относительные пути или исправляйте
`gate_files` профиля. Они отсчитываются от YAML профиля, а не от текущего каталога
команды. Подключённые гейты входят в хеш политики. `gate_files` и inline `gates` несовместимы.
Пустой `gate_files: []` разрешён; каждый перечисленный файл обязателен.

Гейты переходов: id + at + ровно одна коллекция checks или criteria.
Проверки дают свидетельства; PASS гейта разрешает завершить соответствующий этап.
Общие условия фабрики и acceptance checks задачи остаются обязательными.
at: implement.work, implement.docs, implement.verify — для checks;
    implement.review, code-review.complete — для criteria.
Гейты привязаны к этапу, не конкретной роли. Состав команды задаёт граф.
Work/docs допускают только slice checks. Final checks принадлежат verify.
Ранний гейт требует project-checks у автора; WRITES_READY его не обходит.
Verify повторяет все required_checks, в том числе уже пройденные на work.
После FAIL/BLOCKED координатор выбирает владельца исправления и сохраняет бюджеты.
Planning/Decompose сохраняют собственные validators. Decompose дополнительно
поддерживает командный decompose.complete; planning.complete не поддерживается.
Пример предполагает Python API и npm frontend. Команды/инструменты не установлены
и не исполняются самим профилем: runner запускает их только в назначении.
kind: tests, static, build, docs, codegen либо observation.
for у checks допускает только paths_any/path_regex, не роли/процессы/этапы.
level: slice — проверка слайса; final — integration или единственная задача run.
Final не означает автоматически запуск после всех команд без after.
execution.argv — массив аргументов, без shell: &&, $VAR, glob не раскрываются.
cwd — каталог от корня приложения; '.' обозначает корень.
timeout_seconds — целое 1..86400, лимит ОДНОЙ команды, не время работы агента.
inputs — точные дополнительные файлы ОТ КОРНЯ ПРИЛОЖЕНИЯ, даже если cwd другой.
Не каталоги и не glob. Снимок включает scope задачи + inputs.
Дополняйте inputs зависимостями конкретной задачи; обязательные удалять нельзя.
after — ID других checks; без циклов. Все зависимости должны быть применимы
в той же задаче. Runner требует их свежий PASS в том же node/dispatch.

## Проектная проверка декомпозиции

Подключён [гейт](skills/decompose/gate.yaml) и [скрипт](skills/decompose/check.py).
Это минимальный исполняемый пример: проверяет наличие результата задачи;
замените его требованиями проекта. Общий валидатор всё равно обязателен.
Для AniStar отдельный скрипт сохраняет прежние ограничения слоёв и оценки часов.

Гейт запускается общим валидатором графа перед его успешным завершением.
stdin — JSON с tasks и envelopes. stdout — один JSON с status, message и
непустым списком evidence. PASS требует exit 0, FAIL — exit 1, BLOCKED — exit 2.
Несоответствие, отсутствие JSON, падение скрипта или тайм-аут означают BLOCKED.
Нарушение задачи — FAIL. Независимые проверки сохраняют все причины; after
блокирует зависимую команду, если prerequisite не прошёл.
`{python}` означает Python общего валидатора. путь скрипта, cwd и inputs относятся
к корню проекта, как у Implement. inputs включает скрипт и локальные зависимости
из каталога профиля. gate_files остаётся относительно YAML.
FAIL, тайм-аут, изменение политики/артефактов блокируют результат; после исправления
общий валидатор запускается снова. Проверки не входят в required_checks Implement.

Дополнительные инструкции подключайте через rules.file для coordinator/process
 decompose и отдельно worker/roles task-decomposer, task-reviewer. Общая фабрика
не требует словаря слоёв или потолка часов. Скрипт проверяет формализуемые условия,
содержательное качество по-прежнему оценивает TaskReviewer.

Результаты команд — свидетельства, не окончательное разрешение сборки.
Общий assembler проверяет также актуальное ревью TaskReviewer. Только итоговый
PASS decompose.complete разрешает создание локальных задач; реализация не запускается.
